## 📋 СПИСОК ЗАДАЧ

### Задача 1.1: Реализация `AsyncMutex` (замена `FileLock`)

**Проблема**: Текущая реализация `file-lock-utils.ts` содержит race condition в функции `processNextInQueue`:
- Строка 120: `lock.processing = false` устанавливается **перед** проверкой очереди.
- Это может привести к тому, что две операции одновременно начнут выполняться, вызывая коррупцию данных.

**Решение**: Реализовать атомарный `AsyncMutex` с гарантией FIFO и правильной обработкой состояния.

**Файлы для изменения**:
- `src/file-lock-utils.ts` – полная замена текущей реализации.
- `src/utils/async-mutex.ts` – новый файл (если нужно вынести общую утилиту).

**Требования к реализации**:
1. **Атомарность операций**: Установка `processing = true` и извлечение из очереди должны быть атомарными.
2. **Гарантия FIFO**: Операции должны выполняться в порядке поступления (с учетом приоритетов).
3. **Таймауты**: Сохранить текущую логику таймаутов, но гарантировать их очистку.
4. **Очистка ресурсов**: При удалении блокировки очищать все таймеры и ссылки.
5. **Backward compatibility**: Сохранить публичный API `withFileLock<T>(...)` без изменений.

**Критерии приемки (Definition of Done)**:
- [x] Написаны юнит-тесты, симулирующие race condition (10+ конкурентных операций).
- [x] Тесты проходят без потерь данных.
- [x] Время выполнения операций не увеличилось более чем на 20%.
- [x] Все существующие тесты `file-lock-utils.test.ts` проходят.
- [x] Добавлена интеграция с существующими потребителями (`shared-log-storage.ts`, `session-manager.ts`).

### Задача 1.2: Реализация `Atomic Write` (паттерн write-tmp-rename)

**Проблема**: Текущая запись файлов (`fs.writeFile`) не атомарна. При краше процесса во время записи файл может остаться поврежденным.

**Решение**: Внедрить паттерн **write-temporary-rename**:
1. Записать данные во временный файл (`*.tmp`).
2. Валидировать JSON (если применимо).
3. Переименовать временный файл в целевой (`fs.rename` атомарен на большинстве файловых систем).

**Файлы для изменения**:
- `src/shared-log-storage.ts` – метод `saveToFile()` (строки ~200-250).
- `src/utils/atomic-write.ts` – новый модуль для повторного использования.

**Требования к реализации**:
1. **Атомарность**: Использовать `fs.rename` после успешной записи.
2. **Валидация JSON**: Перед переименованием убедиться, что записанные данные – валидный JSON.
3. **Очистка временных файлов**: Удалять старые `.tmp` файлы при старте (возраст > 1 часа).
4. **Обработка ошибок**: При ошибке валидации – не переименовывать, выбрасывать ошибку.
5. **Поддержка Windows**: Учесть особенности файловых систем (разрешения, симлинки).

**Критерии приемки**:
- [x] Создан модуль `atomic-write.ts` с функцией `atomicWriteFile(path, data)`.
- [x] Интегрирован в `SharedLogStorage.saveToFile()`.
- [x] Написаны тесты, симулирующие краш процесса во время записи (использование `mock-fs`).
- [x] Файл никогда не остается в поврежденном состоянии (только целый старый или целый новый).
- [x] Временные файлы очищаются при следующем запуске.

### Задача 1.3: Исправление уязвимостей шифрования

**Проблема**: В `src/encryption-utils.ts`:
1. Hardcoded salt `'salt'` (строка 94).
2. Default secret phrase `'roo-trace-default-secret'` (строка 93).
3. Отсутствие валидации ключа на уникальность для каждого workspace.

**Решение**:
1. Запретить использование default secret phrase в production.
2. Генерировать уникальный salt на основе workspace path.
3. Добавить валидацию ключа (длина, энтропия).

**Файлы для изменения**:
- `src/encryption-utils.ts` – функция `getEncryptionKey()` и добавление новых функций.
- `src/rootrace-dir-utils.ts` – получение уникального идентификатора workspace.

**Требования к реализации**:
1. **Уникальный ключ на workspace**: Использовать `crypto.scryptSync(workspaceId + secretPhrase, uniqueSalt, KEY_LENGTH)`.
2. **Валидация**: Если используется default secret phrase – выбрасывать warning в dev, ошибку в production.
3. **Миграция**: Добавить функцию `migrateEncryptionKey(oldKey, newKey)` для обновления существующих зашифрованных логов.
4. **Конфигурация**: Добавить настройку `rooTrace.encryption.secretPhrase` в VS Code config.

**Критерии приемки**:
- [x] Default secret phrase запрещен в production (проверка `process.env.NODE_ENV === 'production'`).
- [x] Каждый workspace имеет уникальный ключ (даже с одинаковой secret phrase).
- [x] Добавлены юнит-тесты, проверяющие, что два разных workspace дают разные ключи.
- [x] Существующие логи могут быть расшифрованы (миграционный путь).
- [x] В консоль выводится предупреждение при использовании default secret phrase.

### Задача 1.4: Синхронизация HTTP/MCP (версионирование логов MVCC)

**Проблема**: `SharedLogStorage` – singleton, используемый одновременно HTTP и MCP серверами. При конкурентной записи возможна потеря данных (последний writer wins).

**Решение**: Внедрить **Multi-Version Concurrency Control (MVCC)**:
1. Каждая операция записи получает уникальный versionId (timestamp + random).
2. Перед записью проверять, что текущая версия файла равна ожидаемой.
3. При конфликте – повторять операцию с обновленными данными (merge).

**Файлы для изменения**:
- `src/shared-log-storage.ts` – методы `saveToFile()` и `loadFromFile()`.
- `src/types.ts` – добавить поле `versionId` к `RuntimeLog`.
- `src/mcp-handler/handlers/inject-probes.ts` – использование новой схемы синхронизации.

**Требования к реализации**:
1. **Версионирование**: Каждый файл логов содержит метаданные `{ versionId, timestamp, logs: [...] }`.
2. **Оптимистичная блокировка**: При записи проверять `currentVersionId === expectedVersionId`.
3. **Merge при конфликте**: Если версии разошлись, объединять логи (по timestamp) и повторять запись.
4. **Производительность**: Не добавлять значительных накладных расходов (<5% slowdown).

**Критерии приемки**:
- [x] Написаны интеграционные тесты, симулирующие конкурентную запись от HTTP и MCP.
- [x] Ни один лог не теряется при 100+ конкурентных операциях.
- [x] Система обнаруживает и разрешает конфликты (логирование конфликтов).
- [x] Backward compatibility: старые файлы логов (без versionId) загружаются корректно.
- [x] Добавлены метрики количества конфликтов и успешных merge.

### Требования к тестированию

**Для каждой задачи должны быть написаны**:
1. **Юнит-тесты** – проверка логики в изоляции.
2. **Интеграционные тесты** – взаимодействие с файловой системой, конкурентность.
3. **Тесты на race conditions** – использование `setTimeout`, `Promise.all` для симуляции гонок.

**Конкретные тестовые сценарии**:
- **AsyncMutex**: 10 потоков одновременно запрашивают блокировку → проверка порядка и отсутствия потерь.
- **Atomic Write**: Имитация краша процесса (выбрасывание ошибки в середине `fs.writeFile`).
- **Шифрование**: Проверка, что default secret phrase вызывает ошибку в production.
- **MVCC**: HTTP и MCP одновременно пишут логи → проверка, что все логи сохранены.

**Используемые инструменты**:
- `jest` – основной фреймворк.
- `mock-fs` – для изоляции файловой системы.
- `sinon` – таймеры и моки.
